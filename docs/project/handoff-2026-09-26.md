# 1. SYSTEM ARCHITECTURE

## 1.1 What the product is

**Repo-backed — product/requirements/case-core-v0.1.md:** Case Core is the canonical operational spine for one R&R auto-glass job. One Case should survive the full lifecycle from intake through identification, sourcing, pricing, quote/approval, ordering, installation, invoicing, and completion. The currently implemented v0.1 slice is only the foundation: create/read/list a Case, persist vehicle/service context, maintain current state, and maintain durable Case events.

**Repo-backed — architecture/case-core-contract-v0.1.md:** the Case is the canonical operational center. Channel does not fork the domain model. DIRECT, AUCTION, and INSURANCE are values on the same Case model.

**Conversation-only:** do not reduce this product to “a VIN lookup tool.” That was an early demo framing. The actual business outcome is a profitable completed R&R glass job and the customer/channel-facing quote/invoice that gets it there. The VIN lookup is one constrained identification step inside that lifecycle.

**Conversation-only:** the desired full business stages, expressed at a high level, are:

1. intake;
2. identify glass;
3. source inventory;
4. price;
5. produce quote/estimate;
6. obtain approval/authorization;
7. order;
8. install;
9. invoice/close;
10. complete.

That end-state framing matters when making architecture tradeoffs: a technically elegant lookup service that does not help move a Case toward a completed profitable job is the wrong center of gravity.

## 1.2 Repository/component topology

### apps/api

**Repo-backed — apps/api/package.json, apps/api/src/app.ts, apps/api/src/store-factory.ts, apps/api/src/pg-store.ts:** TypeScript + Express API.

Primary implemented endpoints:

- POST /api/v1/cases
- GET /api/v1/cases
- GET /api/v1/cases/:caseId
- GET /api/v1/cases/:caseId/events
- POST /api/v1/cases/:caseId/actions
- GET /health

The action endpoint is currently a reserved boundary: it loads the Case and returns ACTION_NOT_ALLOWED / 409 because workflow actions are not yet implemented.

**Repo-backed — apps/api/src/app.ts:** request validation uses Zod. Create Case currently requires channel, Year/Make/Model, VIN, and glass type. Validation errors return the stable v1-style error envelope.

**Repo-backed — apps/api/src/store-factory.ts:** storage is environment-selected:

- no DATABASE_URL -> JsonCaseStore for local development;
- DATABASE_URL present -> PgCaseStore for deployed environments.

**Repo-backed — apps/api/src/pg-store.ts:** create Case is transactional. It creates Vehicle, Case, Glass Request, CASE_CREATED event, and optional idempotency record atomically.

### apps/web

**Repo-backed — apps/web/package.json, apps/web/src/App.tsx, apps/web/src/api.ts:** React 19 + TypeScript + Vite staff UI.

The implemented staff slice contains:

- Case Queue;
- New Case form;
- Case Detail;
- current state display;
- activity timeline;
- browser create/list/detail/event calls.

**Repo-backed — apps/web/src/api.ts:** browser code talks to VITE_API_BASE_URL. Local default is the local API origin. Deployed builds set it to /api/v1 so browser API calls are same-origin.

**Repo-backed — apps/web/api/proxy.js:** deployed web requests under /api/v1 are proxied server-side to the API Vercel project. The proxy forwards request headers/body, strips problematic hop/cookie headers, and can add the Vercel automation bypass header server-side.

### apps/e2e

**Repo-backed — apps/e2e/playwright.config.ts, apps/e2e/tests/case-core.spec.ts:** Playwright is the browser integration layer.

Current high-value tests prove:

- create Case through the browser;
- wait for the final successful POST /api/v1/cases response;
- Case Detail renders a valid RRA reference and the expected service data;
- CASE_CREATED appears in activity;
- returning to queue shows the specific newly created Case;
- reload preserves that Case;
- the browser path does not expose a paid VIN lookup action.

Traces are configured with retain-on-failure.

The test was deliberately hardened on 2026-09-26 after several staging-only failures:
- ambiguous DIRECT text matched a hidden option;
- Vercel protection produced an intermediate redirect handshake;
- existing staging test data caused strict-mode collisions on duplicate vehicle text.

The current test scopes assertions to the newly-created case reference/card.

**Repo-backed:** no MyGrant adapter or live MyGrant integration currently exists in rnr-workflow. The Case Core contract explicitly keeps provider-specific behavior outside Case Core.

**Conversation-only:** MyGrant was separately validated as an authenticated browser workflow before this Case Core rewrite. The working integration direction is:

- captured/mock responses for normal development to avoid paid calls;
- live MyGrant only when explicitly authorized;
- do not bury MyGrant-specific selectors/session behavior inside Case Core.

## 1.4 API and state contracts

**Repo-backed — architecture/openapi/case-core-v0.1.yaml and architecture/case-core-contract-v0.1.md:** /api/v1 is the contract namespace.

Rules that should remain architectural invariants:

- clients do not PATCH current_state arbitrarily;
- state changes happen through explicit business actions;
- action handlers enforce permission + current state + guards;
- current state update and resulting event commit atomically;
- event history is append-only in normal application flows;
- corrections are later events, not history rewrites;
- event ordering is sequence, not timestamp;
- provider credentials never enter Case/Event payloads.

# 2. ARCHITECTURE DECISIONS

These are written ADR-style so they can later be split into architecture decision records.

## AD-01 — Model the business lifecycle before optimizing a lookup feature

**Decision:** build from the R&R job lifecycle outward, with Case as the operational record.

**Repo-backed — README.md, product/requirements/case-core-v0.1.md.**

**Conversation-only:** this was a deliberate correction to the earlier VIN-demo mindset. The user wanted a Pega/Blueprint-like business-process understanding before deeper automation.

**Alternatives considered:**
- start with a standalone VIN lookup service;
- automate MyGrant first and retrofit workflow later.

**Why chosen:** lookup is only useful if it advances a job to quote/approval/order/install/complete. A Case-centered model prevents the external provider from becoming the product architecture.

**Revisit when:** only if the business itself changes such that R&R no longer needs a long-lived job record.

## AD-02 — One canonical Case model across Direct, Auction, and Insurance

**Decision:** channel is data, not three domain models.

**Repo-backed — product/requirements/case-core-v0.1.md, architecture/case-core-contract-v0.1.md.**

**Alternatives considered:** separate workflows/data models per channel.

**Why chosen:** the same physical glass job needs one operational truth; persona/channel differences belong in projections, terminology, permissions, and approval semantics.

**Revisit when:** only if a channel has legally or operationally incompatible lifecycle/invariants that cannot be expressed as policy over the shared aggregate.

## AD-03 — Modular monolith before microservices

**Decision:** Case Core is a module inside a modular monolith. Provider-specific identification, sourcing, pricing, quote, procurement, install, and notification behavior remain separate module boundaries without separate services yet.

**Repo-backed — architecture/case-core-contract-v0.1.md.**

**Conversation-only:** recommendation was to avoid engineering the team into distributed-system complexity during a fast client product build.

**Alternatives considered:** service-per-capability/microservices; provider service as the system center.

**Why chosen:** current scale/team do not justify distributed transactions, service discovery, independent deploy complexity, or cross-service observability.

**Revisit when:** independently scaled/deployed modules have a demonstrated operational need, not as an abstract cleanliness preference.

## AD-04 — Explicit business actions, not arbitrary Case mutation

**Decision:** workflow state changes through POST /cases/:id/actions, never generic PATCH current_state.

**Repo-backed — architecture/case-core-contract-v0.1.md, product/requirements/case-core-v0.1.md, apps/api/src/app.ts.**

**Alternatives considered:** CRUD Case PATCH endpoint; frontend-owned state transitions.

**Why chosen:** guards, permissions, event emission, and business side effects need a single server-owned transition boundary.

**Revisit when:** do not revisit the principle. Specific action transport can evolve, but arbitrary state mutation should remain forbidden.

## AD-05 — Append-only Case events without making the entire system pure event sourcing

**Decision:** maintain a current Case projection plus durable append-only Case events.

**Repo-backed — architecture/case-core-contract-v0.1.md, migration 001_case_core.sql.**

**Alternatives considered:** mutable audit rows; full event-sourced aggregate with all state reconstructed from events.

**Why chosen:** R&R needs auditability/history but does not yet need full event-sourcing complexity.

**Revisit when:** event replay/versioned projections become a real requirement, or regulatory/audit requirements become stronger.

## AD-06 — Separate Customer, Vehicle, Glass Request, and Case identities

**Decision:** keep these as separate entities/relationships.

**Repo-backed — architecture/case-core-contract-v0.1.md.**

**Alternatives considered:** flatten all intake fields directly on Case.

**Why chosen:** future vehicle reuse, customer lifecycle, and multi-glass extension remain possible without forcing them into v0.1.

**Revisit when:** not the separation itself; revisit vehicle dedupe and multi-glass cardinality after client validation.

## AD-07 — Reversible provisional defaults

**Decision:** implement unresolved client choices as reversible defaults, not “approved facts.”

**Repo-backed — validation/client-validation-register-v0.1.md; issue #22 disposition.**

**Alternatives considered:** block all implementation until client answers every open question; silently hard-code assumptions.

**Why chosen:** the 48-hour build required progress, but architecture should not launder assumptions into policy.

**Revisit when:** each provisional item is client-validated/revised.

## AD-08 — Local JSON, deployed PostgreSQL

**Decision:** JsonCaseStore for local frictionless work; PostgreSQL for staging/production.

**Repo-backed — apps/api/src/store-factory.ts, docs/platform/case-core-deployment-v0.1.md.**

**Alternatives considered:** force PostgreSQL for every local test; deploy JSON/filesystem persistence.

**Why chosen:** Vercel filesystem is not durable application persistence, while local JSON makes basic development simple.

**Revisit when:** developer environment consistency makes local Postgres preferable, or testcontainers become worthwhile.

## AD-09 — PostgreSQL transaction owns Case creation integrity

**Decision:** Case, Vehicle, Glass Request, CASE_CREATED event, and idempotency record are one transaction.

**Repo-backed — apps/api/src/pg-store.ts.**

**Alternatives considered:** sequential independent writes; provider lookup inside the same transaction.

**Why chosen:** a successful Case must never exist without its core records/event; external provider latency/cost must not hold DB transactions open.

**Revisit when:** no reason to weaken atomicity. Additional modules should use explicit transaction/outbox boundaries.

## AD-10 — Idempotency is required for financially/operationally meaningful writes

**Decision:** create Case accepts Idempotency-Key and maps it durably.

**Repo-backed — migration 001_case_core.sql, apps/api/src/app.ts, apps/api/src/pg-store.ts.**

**Conversation-only:** this principle is stronger for future paid VIN lookup and ordering: retries must not create repeat charges or repeat purchases.

**Alternatives considered:** trust frontend double-click prevention; ignore replay until later.

**Why chosen:** network retries and agents will replay requests.

**Revisit when:** mechanism can change, requirement should not.

## AD-11 — MyGrant is behind a provider adapter and is not in Case Core

**Decision:** identification provider behavior belongs behind a provider boundary with mock/live modes.

**Repo-backed:** architecture contract keeps provider behavior outside Case Core.

**Conversation-only:** explicit mock/live adapter was chosen to avoid roughly dollar-scale paid VIN calls during development and to keep browser automation replaceable if a supported API becomes available.

**Alternatives considered:** hard-code Playwright selectors in Case Core; call live provider in tests; wait for perfect official API access before building identification.

**Why chosen:** cost control, provider fragility, test determinism, and future API migration.

**Revisit when:** MyGrant provides a supported stable API and terms/permissions are clear. Replace implementation behind the interface, not the domain model.

## AD-12 — YMM-first identification, VIN only as ambiguity fallback

**Decision:** YMM is always first. Paid VIN lookup is constrained by glass type and ambiguity.

**Conversation-only.**

**Alternatives considered:** VIN-first; VIN for every Case; staff discretion without system guardrails.

**Why chosen:** VIN calls consume credits/cost and are unnecessary for many parts.

**Revisit when:** provider economics or catalog accuracy materially change, with product approval.

## AD-13 — Human gates around ambiguity, pricing exceptions, purchases, and consequential external side effects

**Decision:** agents can automate preparation and deterministic decisions, but ambiguous glass choice, exception pricing, actual purchase, and real client validation remain human-controlled unless explicitly delegated.

**Conversation-only; partially reflected in lane instructions and validation issue policy.**

**Alternatives considered:** end-to-end autonomous purchasing/validation.

**Why chosen:** these are consequential business/financial actions and current evidence/permissions are incomplete.

**Revisit when:** the business explicitly defines autonomous thresholds and audit/rollback behavior.

## AD-14 — Separate Vercel web and API projects

**Decision:** apps/web and apps/api are separate Vercel projects.

**Repo-backed — docs/platform/case-core-deployment-v0.1.md.**

**Alternatives considered:** one combined Vercel project; other hosting such as the earlier Render direction.

**Why chosen:** preserves frontend/backend boundaries while staying operationally simple.

**Revisit when:** a single deployment unit reduces complexity without weakening API boundaries, or platform requirements change.

## AD-15 — Same-origin web proxy for deployed browser API calls

**Decision:** browser talks to /api/v1 on the web origin; Vercel web serverless proxy calls the protected API deployment.

**Repo-backed — apps/web/api/proxy.js, apps/web/src/api.ts, deploy-staging.yml.**

**Alternatives considered:** browser calls protected preview API directly; CORS + Vercel bypass-cookie handshake from browser.

**Why chosen:** staging testing showed protection redirects/cookies made direct browser-to-API behavior brittle. Same-origin proxy keeps the bypass secret server-side.

**Revisit when:** stable custom domains/application auth remove the preview-protection constraint. Keep secrets server-side regardless.

## AD-16 — Staging is a durable branch and production promotes the exact tested staging SHA

**Decision:** main does not deploy directly to production. A deliberate main -> staging promotion triggers live smoke. Production workflow requires exact staging HEAD.

**Repo-backed — docs/platform/case-core-deployment-v0.1.md, deploy-staging.yml, promote-production.yml.**

**Alternatives considered:** main auto-deploys production; rebuild arbitrary main head; production from an untested newer commit.

**Why chosen:** gives a simple provenance chain from tested staging state to production.

**Revisit when:** artifact-based promotion is introduced. An immutable built artifact would be stronger than rebuilding source from the SHA, but exact-SHA source promotion is acceptable for this phase.

## AD-17 — Supabase RLS blocks direct browser roles; Express is the application boundary

**Decision:** enable RLS and define no anon/authenticated policies for Case Core tables.

**Repo-backed — migration 002_enable_case_core_rls.sql.**

**Alternatives considered:** expose Supabase tables directly to browser with policies.

**Why chosen:** domain/action authorization belongs in the API; direct table access would create a second authorization model.

**Revisit when:** there is a concrete need for direct Supabase access and policies can express the same domain authorization safely.

## AD-18 — Authentication deferred, but this means “demo/internal,” not “production-ready”

**Decision:** do not block Case Core foundation on auth; explicitly prevent that from being interpreted as launch readiness.

**Repo-backed — docs/platform/case-core-deployment-v0.1.md, issue #28 checklist, future issue #73.**

**Alternatives considered:** build auth before proving Case Core; expose current deployment as real customer production.

**Why chosen:** speed for the vertical slice, with a hard later security gate.

**Revisit when:** before any unrestricted real customer/staff usage.

## AD-19 — GitHub Issues + Project are durable orchestration state; runtime is replaceable

**Decision:** issues are executable work packets, workflow labels route lanes, Project #10 is a current-state projection, and the execution runtime is vendor-neutral.

**Repo-backed — docs/project/agentic-delivery-control-plane-v0.1.md, .github/agentic/*.json.**

**Alternatives considered:** orchestration state only in ChatGPT conversations; vendor-specific agent scheduler as source of truth.

**Why chosen:** agents are replaceable. Repository/GitHub state must survive this exact handoff scenario.

**Revisit when:** only if a replacement control plane can preserve equivalent durable state and auditability.

## AD-20 — Human/client validation cannot be synthesized by an agent

**Decision:** type:validation routes to Human Validation and no agent assignment.

**Repo-backed — dispatch-config.json, dispatch-issue.sh.**

**Alternatives considered:** agent infers approval from context.

**Why chosen:** a consequential human decision is not valid because an AI predicts what the human would say.

**Revisit when:** never for actual human/client approval; only change which decisions require that gate.

## AD-21 — Focused PRs and clean main over “agent writes directly to main”

**Decision:** work starts from main on a focused branch and returns through a PR.

**Repo-backed — lane-instructions.json and control-plane docs.**

**Conversation-only:** the user repeatedly reinforced “main stays clean,” branch/commit/PR discipline, and wanted autonomous progress without losing reviewable checkpoints.

**Revisit when:** trivial automation-only changes may someday use trusted bots, but keep auditability.

## AD-22 — Strict branch protection was recommended but is not currently enforced

**GitHub state:** main and staging are currently unprotected.

**Conversation-only:** earlier architecture recommendations included PR-only protected branches and environment gates. The user accepted being the human bottleneck rather than pretending agent reviews were independent human approvals.

**Why current state exists:** speed and single-owner workflow during the hackathon.

## AD-23 — Extract the reusable agentic workspace only after the vertical slice proves itself

**Conversation-only:** R&R is Experiment 001 for a reusable “zipped SDK” / turnkey agentic-engineering workspace. The user explicitly wants to extract the reusable setup, but not before enough real vertical-slice delivery exposes the true requirements.

**Alternatives considered:** generalize the agent platform first.

**Why chosen:** premature framework extraction would optimize imagined workflows.

# 5. HOW WORK ACTUALLY GETS DONE

## 5.1 Intended issue lifecycle

**Repo-backed — agentic control-plane files:**

1. PM creates an issue with exactly one workflow:* label plus milestone/priority/type labels.
2. Dispatcher checks case-core-dependencies.json.
3. If prerequisites are open -> Backlog.
4. If type:validation -> Human Validation; no runtime can execute the decision.
5. Otherwise dispatcher sets Ready and writes an Agent Work Packet to the issue.
6. Approved runtime comments /agent start.
7. agent-runtime-state.yml sets In Progress.
8. Runtime branches from main, does focused work, tests it, opens a PR referencing the issue.
9. project-pr-status.yml moves linked issue to In Review.
10. Human reviews/accepts consequential work.
11. Merge/issue close moves Done.
12. issue close causes dispatcher to re-evaluate direct dependents.

## 5.2 What happened in the Case Core pilot

**Conversation-only + GitHub issue comments:** ChatGPT was both orchestration director and the active execution runtime for many lanes.

Typical actual loop:

1. User and ChatGPT agreed the next slice.
2. ChatGPT inspected current repository/issues.
3. Dispatcher/work packet existed or ChatGPT manually triggered the intended state.
4. ChatGPT posted /agent start with runtime/lane/scope.
5. ChatGPT used connected GitHub tools to create a branch, write code/docs/tests, open a focused PR, inspect CI, and fix failures.
6. User acted as the real human acceptance gate in chat when a consequential design/product decision needed acceptance.
7. ChatGPT recorded that acceptance durably in the issue/artifact.
8. PR was merged.
9. Closing the issue released the next dependency.

Important: the control plane did not itself spawn an autonomous coding worker. It prepared durable work packets and state transitions; ChatGPT manually claimed and executed them.

Y can improve this by actually running on a schedule, but should preserve the durable issue/claim/PR protocol so scheduled autonomy does not become invisible work.
